## Outstanding risks

| ID | Risk | Mitigation / status |
| --- | --- | --- |
| R-01 (closed 2026-11-16) | Constraints and triggers applied on PostgreSQL (owner, 2026-11-16) but not yet exercised by tests | `pnpm test:int` (T-MIG-001..006). Closed: T-MIG-001..006 / T-AUTH-INT-001 pass on macOS (14/14) |
| R-02 | Request-level tenant isolation now verified on PostgreSQL (T-TEN-INT-001, macOS); CI has never run | CI after an approved push |
| R-03 | Agent Teams through OpenRouter: provider and model behaviour unverified; credentials live in the owner's shell profile | Resolve the local `401 User not found`; never place keys in the repository |
| R-04 | pgcrypto key: no rotation tooling yet; losing `EMR_ENCRYPTION_KEY` makes encrypted clinical text unreadable | Owner backs up the key; rotation script (re-encrypt in batches) before production (Phase 14) |
| R-05 | Twilio trial and Indian SMS (DLT) restrictions for real SMS | Local SMS inbox in development (DEC-011); document limits |
| R-06 | ESLint 9 is marked deprecated upstream | Revisit after Phase 1; no security impact today |
| R-08 | Account enumeration: register returns 409 EMAIL_IN_USE (standard sign-up behaviour); login, resend and forgot-password answer generically | Auth rate limit; accepted trade-off, revisit if required |
| R-09 (closed 2026-11-16) | Auth flows verified only against in-memory Prisma/Redis so far | T-AUTH-INT-001 on macOS after the migration. Closed: T-MIG-001..006 / T-AUTH-INT-001 pass on macOS (14/14) |
| R-10 | Prisma drops undeclared keys: drift check found the 4 SQL-only same-tenant keys (now declared, DEC-031); CHECKs, exclusions and triggers remain outside Prisma | `sql-drift.spec.ts`; every migration `--create-only` + review; `prisma:drift` after each migration |
| R-11 (interim, until P14-09) | One database login for everything: any process holding the application's credentials could write a system quarantine row (M-09 Layer A guarantees only that it is a correct one: expired batch, true quantity, today's report, same transaction). In development the login is the Docker superuser, which can disable triggers | **Mandatory** Phase 14 task P14-09: separate accounts for migrations, application and jobs; application never owner or superuser |
| R-12 (Phase 8, open until the API exists) | The GSTIN exclusion constraint (DEC-050) is race-safe, but PostgreSQL's error detail names the other hospital's id and GSTIN | The registrations API must map the constraint to `409 GSTIN_UNAVAILABLE` with a message naming no hospital and must never return or log the database error text to the user; HTTP test that the response carries no foreign id (8-B2) |
| R-13 (interim, until P14-09) | Platform reference data (`statutory_room_tax_rules`) is append-only in the database, but the application's login could still insert a new rule row, because the database cannot tell a migration from the application (same reason as R-11) | No application writer exists (code review; test that the room-rule repository exposes only reads); separate database accounts in P14-09 remove insert rights from the application |
| R-15 (Phase 8, by design) | Effective-dated tax checks depend on time: a commit can become visible long after its last check (storage or replication stall), and any client can run `SET CONSTRAINTS ALL IMMEDIATE` to check early (DEC-058) | Writers hold row locks until commit; M-11b readers take `FOR SHARE` in the order hospital, then classification, so issued lines always match committed tax data (8-A2); idle and statement timeouts for application roles (P14-09); the ten-minute margin is documented as a margin, not a guarantee |
| R-16 (Phase 8, by design) | Tax configuration writes serialise per hospital (DEC-058, DEC-059): at REPEATABLE READ or SERIALIZABLE the losing transaction fails with a serialization error; a transaction that updates a classification and then writes other tax data for the same hospital takes locks in reverse order and can be cancelled as a deadlock (not tested). Integrity is not at risk in either case: the database refuses or cancels, it never stores an inactive default or a version on an inactive classification | The tax settings API locks the hospital row first in every tax-settings transaction and retries or reports SQLSTATE 40001 and 40P01 (8-B2); the application currently uses READ COMMITTED (no isolation level is set), where the later transaction waits and is refused |
| R-14 (release gate) | Tax outcomes depend on each hospital's configuration and on law that changes; MedCore implements the rules but is not a tax adviser | Mandatory accountant review before production use (DEC-054, TASKS 8-G1); classifications versioned and invoices snapshotted so a correction never rewrites history |
| R-07 | CI workflow has never run on GitHub (nothing pushed) | Push only with owner approval; then verify CI |
